### M-202 — Show 'Approved.' on a Telegram tap only when core actually accepted it
- **Severity:** medium · **Effort:** trivial · **Impact:** security, reliability
- **Locations:** `packages/laravel-capabilities-messaging/src/Telegram/CallbackHandler.php:127`, `packages/laravel-capabilities-messaging/src/Telegram/ProcessTelegramUpdate.php:361`, `packages/laravel-capabilities/src/Approval/ApprovalManager.php:402`, `packages/laravel-capabilities-messaging/tests/Unit/Telegram/CallbackRoutingTest.php:66`
- **Current:** CallbackHandler returns status 'ok' whatever CapabilityResult ApprovalGateway::accept()/reject() gives back. Core's approval policy check (requester_or_role by default, role:<name>, any_staff), lost double-tap races (conflict), expiry and execution failures all come back as failure results. They reach the tapper as the toast 'Approved.' and ProcessTelegramUpdate logs no warning (ok=true).
- **Recommended:** The handler maps a non-ok result to its own status: forbidden, already_handled for conflict and expired, and a failed status for an execution failure. The toast then tells the truth ('You are not allowed to decide this approval.' and so on), and the update result is ok=false with the error code.
- **Why it matters:** In a group chat the buttons are visible to every member. Under the default policy, a linked member who is neither the requester nor a role holder taps Accept, is told 'Approved.', and nothing happens. The approval then sits pending until it expires while the requester believes it was approved. The same happens to a requester tapping on a role:<name> capability. The existing routing test even pins ok=true for an accept that core failed closed.
- **How to fix:** In CallbackHandler::handle after the gateway call: `if (! $result->isOk()) return ['status' => match ($result->errorCode()) { 'forbidden' => 'forbidden', 'conflict', 'expired' => 'already_handled', 'not_found' => 'not_found', default => 'failed' }, 'result' => $result, 'message' => $result->errorCode() ?? 'failed'];`. Add a 'failed' toast in callbackToast and a unit test where the ApprovalManager policy denies the tapper.

### X-201 — Split's single concurrency group can drop a pending tag mirror
- **Severity:** medium · **Effort:** trivial · **Impact:** reliability
- **Locations:** `.github/workflows/split-packages.yml:30`, `.github/workflows/split-packages.yml:129`, `docs/versioning.md:50`
- **Current:** Every split run (main pushes and v* tags) shares the concurrency group `split-packages`. `cancel-in-progress: false` protects only the running run. GitHub keeps at most one pending run per group, and a newer queued run cancels the pending one. Take a tag pushed while a main split is in progress, for example `release.sh --squash`, which pushes main and then the tag within seconds. The tag run waits as pending, and any later push to main in that window (the fix loop merged 42 commits today) cancels it. That tag then never reaches the package remotes, Packagist or the CLI GoReleaser. versioning.md:50 says runs 'queue one after another'.
- **Recommended:** Tag runs never share a pending slot with main runs. After X-101, a tag run pushes only `refs/tags/<tag>` and a main run pushes only `main`, so the race the global group was added for (both pushing package main, 'cannot lock ref') is gone. A per-ref group is enough. Main runs still serialize, and a newer pending main run replacing an older one is correct because the latest tree wins.
- **Why it matters:** The global group was the fix for main and tag runs both pushing package-remote main. X-101 removed that shared ref, so the global group now only adds a way to lose a release publication. The cancellation shows up only as a 'cancelled' run in Actions. Nothing tells the releaser that Packagist or CLI binaries are missing for the tag, and release.sh has already pushed the tag and refuses to reuse it.
- **How to fix:** split-packages.yml: `concurrency: { group: split-packages-${{ github.ref }}, cancel-in-progress: false }`. Rewrite the lines 30-33 comment to say the main-vs-tag race ended with tag runs no longer pushing main (X-101). Update docs/versioning.md:50 to match: main runs serialize and the newest main wins, and each tag has its own group. A tag run that overlaps a main run may point at a side commit whose parent is the previous package main. That is the same shape hotfix tags already have (versioning.md:25).

### M-201 — Stop a Telegram notify failure from turning an approval into an internal error
- **Severity:** medium · **Effort:** small · **Impact:** reliability, security
- **Locations:** `packages/laravel-capabilities-messaging/src/Notifiers/TelegramApprovalNotifier.php:38`, `packages/laravel-capabilities-messaging/src/Notifiers/TelegramApprovalNotifier.php:117`, `packages/laravel-capabilities/src/Approval/ApprovalManager.php:359`, `packages/laravel-capabilities/src/Pipeline/InvokePipeline.php:227`
- **Current:** Since the M-101/L-101 fixes the Telegram notifier really runs inside ApprovalManager::request(), after store->put() and the approval.requested audit. The notifier rethrows any Bot API failure (429, 5xx, bot blocked, chat not found), and with telegram.enabled=true but a missing token or webhook secret it throws for every approval, HTTP and CLI included, because requireTelegramSecrets() runs before the chat_id skip. request() has no try/catch, so the pipeline returns `internal` instead of approval_required.
- **Recommended:** Notifier failures never change the approval outcome. The row stays pending, the caller gets approval_required with its id, the failure is audited (approval.notify_failed) and logged, and the remaining notifiers still run. Rows with no chat target return before any secret check.
- **Why it matters:** Right now a failed notification leaves a pending row that an HTTP or CLI approver can still accept, while the requester (and, over Telegram, the agent's reply) was told the request failed. So an action the user believes failed can still execute later. Each retry from chat then creates another orphan row. This is the same isolation rule L-103 applied to bus listeners (a side channel must not change the domain outcome), and it only started to matter once M-101 wired the notifier in.
- **How to fix:** In TelegramApprovalNotifier::notifyPending move resolveChatId() and the empty-id return above requireTelegramSecrets(). Then pick one owner for isolation. Preferred: core ApprovalManager::request wraps each notifyPending in try/catch and reports through its audit and PSR logger, which covers host notifiers too. Alternative: the Telegram notifier audits and returns instead of rethrowing. Update NotifierDeliveryAuditTest ('audited and rethrown') to match, and add a unit test: a throwing notifier still yields approval_required and a pending row.
- **Cross-reference:** Same root cause as L-201 (core owns the fix). Not merged: titles share one token (Jaccard 0.05), below the 80% dedupe rule. Ship with L-201 in one PR.

### L-201 — Isolate approval notifiers and the ApprovalRequested listener after the row is saved
- **Severity:** medium · **Effort:** small · **Impact:** reliability
- **Locations:** `packages/laravel-capabilities/src/Approval/ApprovalManager.php:360`, `packages/laravel-capabilities/src/Approval/ApprovalManager.php:349`, `packages/laravel-capabilities/src/Pipeline/InvokePipeline.php:760`, `packages/laravel-capabilities/src/Pipeline/InvokePipeline.php:228`, `packages/laravel-capabilities/src/Pipeline/IdempotencyGuard.php:203`, `packages/laravel-capabilities/src/Registry/CapabilityRegistry.php:769`, `packages/laravel-capabilities-messaging/src/Notifiers/TelegramApprovalNotifier.php:38`
- **Current:** Since L-101, bound notifiers really fire. ApprovalManager::request() saves and audits the row, then calls each notifyPending() without a guard. The Telegram notifier rethrows Bot API failures, and it throws for every approval (HTTP/CLI too) when Telegram is enabled without secrets, because the secrets check runs before the chat-id check. The L-103 fix isolated listeners in the finalizer, ApprovalManager and ApprovalExecutor, but it missed the CapabilityApprovalRequested dispatch in buildApprovalRequired. Either throw reaches finishUncaught: the caller gets 'internal', the pending approval row stays, and a keyed invoke's idempotency row is stored as 'failed'.
- **Recommended:** Once the approval row is saved, a notifier or listener failure must not change the outcome. Report it (ExceptionHandler + metric), keep going to the next notifier, and return approval_required as usual. This is the same rule L-103/L-104 set for listeners and audit.
- **Why it matters:** The failure is not only cosmetic. With an Idempotency-Key (the CLI sends one on every run), the L-102 fix runs the accepted execution under that key. The lookup then finds the 'failed' row and replays 'internal', so an approver who accepts the orphan row burns the approval and the capability never runs. Without a key, the client retries after 'internal' and opens a second approval, and both can be accepted, which is a double execution (D-005 retries must not double-apply). A Telegram outage or a half-configured messaging install is enough to trigger it.
- **How to fix:** ApprovalManager::request(): wrap each `$notifier->notifyPending($row)` in try/catch(Throwable) → FailureReporter::reportAndCount($e, 'approval_notify_failed_total', ['notifier' => $notifier::class]). InvokePipeline::buildApprovalRequired(): send the event through `$this->results()->dispatch($requested)` (the isolating dispatcher) instead of `$this->events?->dispatch()`. Unit tests with InMemoryApprovalStore + InMemoryIdempotencyStore: (1) a notifier whose notifyPending throws → invoke returns approval_required, the key row is pending_approval, and a second notifier is still called; (2) a Dispatcher fake throwing on CapabilityApprovalRequested → same outcome, exception reported once. Optionally, in messaging, move requireTelegramSecrets() after the chat-id early return.
- **Cross-reference:** Same root cause as M-201: ApprovalManager::request() calls notifyPending() with no guard after the row is saved. One core fix (try/catch per notifier, isolating dispatch for CapabilityApprovalRequested) closes both; M-201 adds the messaging-side chat-id-before-secrets reorder and the NotifierDeliveryAuditTest update.

### M-204 — Deliver agent replies longer than Telegram's 4096-character limit
- **Severity:** medium · **Effort:** small · **Impact:** reliability
- **Locations:** `packages/laravel-capabilities-messaging/src/Telegram/TelegramAdapter.php:75`, `packages/laravel-capabilities-messaging/src/Telegram/ProcessTelegramUpdate.php:253`, `packages/laravel-capabilities-messaging/src/Telegram/ProcessTelegramUpdate.php:398`, `packages/laravel-capabilities-messaging/src/Support/TelegramBotApiException.php:30`
- **Current:** The AgentTurn text goes to sendMessage as it is. Telegram rejects text over 4096 characters (and empty text) with 400. That maps to validation_failed, which is not retryable, so sendReply throws a terminal error: the update ends ok=false with no reply, after the agent turn and any tool invokes have already run. Nothing in messaging splits or checks the text length.
- **Recommended:** The adapter splits a long reply into consecutive messages of at most 4096 characters (on paragraph or line boundaries where possible, same chat and topic) and replaces empty text with a short fallback. A reply that still cannot be sent is logged with the reason.
- **Why it matters:** LLM answers over 4096 characters are common: lists, summaries, a reply to several tool results. The user then gets silence after the side effects already happened, which is the outcome M-102 set out to remove.
- **How to fix:** TelegramAdapter::reply: `foreach (self::chunks($text, 4096) as $part) $this->bot->sendMessage($chatId, $part, $params);` using mb_str_split, or a boundary-aware splitter on mb_ strings. Map '' to a fixed fallback such as 'Done.'. For the pending-reply retry, keep the index of the last chunk that was sent so a retry does not resend earlier chunks. Unit-test 4097- and 9000-character replies against FakeTelegramBotClient.

### M-205 — Keep the Telegram agent turn at most once when the job is killed mid-turn
- **Severity:** medium · **Effort:** small · **Impact:** reliability
- **Locations:** `packages/laravel-capabilities-messaging/src/Telegram/ProcessTelegramUpdateJob.php:18`, `packages/laravel-capabilities-messaging/src/Telegram/ProcessTelegramUpdate.php:177`, `packages/laravel-capabilities-messaging/src/Telegram/ProcessTelegramUpdate.php:239`, `packages/laravel-capabilities-messaging/src/Telegram/ProcessTelegramUpdate.php:249`
- **Current:** The M-103 fix makes a retry skip the turn only when a pending reply was cached, and that happens only after a transient send failure. Each update now makes two agent calls (respond and respondWithResults) plus tool invokes, inside a job with no timeout of its own (worker default --timeout=60) and 3 tries. A worker timeout, crash or deploy mid-turn redelivers the update. That runs a fresh agent turn, whose tool calls only replay when the new LLM answer repeats the same capability and input at the same index.
- **Recommended:** Once an update's agent turn has started, a redelivery never starts another. The job records a per-update 'turn started' marker (cache add) before conversation_ingress. A redelivery that finds the marker and no pending reply ends the update without calling the agent (optionally a fixed 'please resend' reply) and logs it. The job declares a $timeout sized for two agent calls.
- **Why it matters:** User-guide:192 and the class doc now promise 'the agent turn and its tool calls run once per update'. Worker timeouts are the most likely way that promise breaks, because two LLM calls can easily pass 60s, and the result is the duplicate or divergent mutations M-103 was about.
- **How to fix:** In process(), after the pending-reply check and link handling: `if ($key !== null && $this->pendingReplies !== null && ! $this->pendingReplies->add($key.':turn', true, self::PENDING_REPLY_TTL)) throw new RuntimeException('turn_already_started');` (terminal). Add `public int $timeout = 110;` to ProcessTelegramUpdateJob and note in the docs that the queue's retry_after must exceed it. Unit test: a second handle() of the same update after an interrupted first one never calls the AgentTurn.

### X-202 — /release makes --squash the default, which rewrites PR-merged public main
- **Severity:** medium · **Effort:** small · **Impact:** reliability, dx
- **Locations:** `.claude/commands/release.md:46`, `.claude/commands/release.md:102`, `scripts/release.sh:366`, `scripts/release.sh:493`, `.claude/commands/release.md:71`
- **Current:** Since the X-102 fix, `--squash` works: its base is the last tag reachable from HEAD (v0.5.2). origin/main has 216 commits since v0.5.2, 91 of them GitHub PR merges ('Merge pull request #126 …'). The agent command tells the agent to prefer `--squash` whenever the history is 'noisy merge' commits, which it always is on this repo, and gives `--yes --squash patch` as the standard follow-up example. Following it collapses all 216 public commits into one and force-with-lease pushes main. Open PR branches and the `.worktrees/*` checkouts are all based on the old main. The v0.5.x releases did not squash. Secondary: step 2 tells the agent to read the gate list from `release.sh --help`, but `usage()` prints only options. Optionally, in release.sh, use `SQUASH_BASE=origin/$BRANCH` whenever it exists, so a squash only touches commits not yet on origin; the tag-based base then remains only for the first-release case. Add a test-release.sh case asserting that base. Add a 'Gates:' block to `usage()` (the same five lines as the header comment), or change release.md:71 to point at `--dry-run`, which prints them.

### L-202 — Remove the approval executor's second idempotency writer (dead in production)
- **Severity:** low · **Effort:** small · **Impact:** maintainability, reliability
- **Locations:** `packages/laravel-capabilities/src/Approval/ApprovalExecutor.php:233`, `packages/laravel-capabilities/src/Approval/ApprovalExecutor.php:363`, `packages/laravel-capabilities/src/Approval/ApprovalManager.php:232`, `packages/laravel-capabilities/src/CapabilitiesServiceProvider.php:154`, `packages/laravel-capabilities/tests/Unit/Approval/ApprovalStateMachineTest.php:285`
- **Current:** After L-102, the approved execution runs through the pipeline under the row's idempotency key, and the pipeline moves that key from pending_approval to completed or failed. ApprovalExecutor::completeIdempotency still writes the same row a second time, always as status 'completed', even when the result failed. Only ApprovalManager::withIdempotency() enables it, and neither the provider nor ContainerBindings::makeApprovalManager ever calls that, so it never runs in production. The approval idempotency tests (ApprovalStateMachineTest:285, ApprovalCrashRecoveryTest:131) wire it through test helpers, so they prove a path hosts never run.
- **Recommended:** One writer for the idempotency row: the pipeline. Remove withIdempotency/completeIdempotency from ApprovalManager and ApprovalExecutor. Re-point the approval idempotency tests at the registry path (executeApproval under the key → row completed/failed, retry replays).
- **Why it matters:** Two mechanisms for one invariant, only one of them live, is how the L-101/L-102 class of bug arose: tests passed on a manager that production never built. If a host did wire it, it would overwrite the pipeline's 'failed' with 'completed'. A different-hash retry would then get 409 conflict instead of the stored failure replay.
- **How to fix:** Delete ApprovalExecutor::completeIdempotency and its call, the $idempotency ctor param and withIdempotency on both classes, and the idempotency entries in tests/Fixtures/ApprovalHelpers.php and tests/Support/SharedFakes.php. Rewrite ApprovalStateMachineTest:285-320 and ApprovalCrashRecoveryTest:131 against a registry with InMemoryIdempotencyStore + InMemoryApprovalStore: invoke with key → approval_required; accept → key row status completed; a failing run() → key row status failed. Keep coverage at 95% or above.

### M-206 — Count 429 retry waits in the Anthropic timeout vs claim_ttl guard
- **Severity:** low · **Effort:** small · **Impact:** reliability
- **Locations:** `packages/laravel-capabilities-ai/src/Support/ContainerBindings.php:141`, `packages/laravel-capabilities-ai/src/Support/AnthropicLlmClient.php:224`, `packages/laravel-capabilities-ai/src/Support/AnthropicLlmClient.php:290`, `packages/laravel-capabilities-ai/config/capabilities-ai.php:72`
- **Current:** The M-104 guard only checks timeout < claim_ttl (110 < 120). One complete() call can take (max_retries+1) timeouts plus up to 60s of Retry-After sleep per retry. With the defaults, a single 429 that says 'retry after 10s' followed by a slow reply passes 120s. The worker is then killed mid-request, and the turn waits for the stale reaper instead of failing as a retryable timeout.
- **Recommended:** One complete() call keeps its whole retry sequence within the job budget. The 429 retry callback stops retrying once elapsed + delay + timeout would pass claim_ttl minus a margin, and throws RetryableLlmException with retry_after_seconds instead.
- **Why it matters:** The guard's own message says the goal is that one request fits the turn job. Retries were left out, so the defaults can still break that goal on a common transient (rate limiting under load). This is not the recorded max_tokens decision. It is the timeout validation that the deferred list says is now in place.
- **How to fix:** Pass a deadline (claim_ttl - 5) into AnthropicLlmClient. In the Http::retry `when` callback, return false when (now - start) + retryDelay + timeout > deadline, so the 429 surfaces as RetryableLlmException with its Retry-After. Unit-test it with Http::fake returning 429 with Retry-After: 30 under a 110/120 budget.
