### C-101 — Stop following HTTP redirects; a 301'd invoke runs describe and exits 0
- **Severity:** high · **Effort:** small · **Impact:** reliability, security
- **Locations:** `packages/capabilities-cli/internal/api/client.go:49`, `packages/capabilities-cli/internal/api/client.go:64`, `packages/capabilities-cli/internal/api/client.go:262`, `packages/capabilities-cli/internal/auth/store.go:135`, `packages/capabilities-cli/internal/auth/session.go:43`, `packages/laravel-capabilities/src/Http/RouteTable.php:107`
- **Current:** The API client uses Go's default redirect policy. On a 301/302/303, Go replays a POST as a GET with no body and keeps the Bearer header on the same host. So with `--base-url=http://host` against an HTTPS-only host (nginx/Forge/Cloudflare 301), `run` / domain-verb POST /capabilities/{name} becomes GET /capabilities/{name}. That is the describe route, which returns `{"ok":true,...}`. InvokeCapability's fail-closed check passes, and the CLI prints the describe payload and exits 0 without running the capability. `auth login --token` accepts and stores that http:// URL because its verification GET follows the redirect. The token is also sent in cleartext on every first hop.
- **Recommended:** The capability API client never follows redirects. Any 3xx becomes a structured error (exit 1, or a validation exit for login) that names the Location and tells the user to use that URL as --base-url. Login therefore refuses a redirecting base URL before storing it.
- **Why it matters:** This breaks the CLI's core promise: exit 0 plus an ok envelope on stdout means the capability ran (docs/agents.md: agents branch on exit code). Here an agent or script is told a mutating write succeeded when the server only returned catalog metadata. The capability API has no legitimate redirects: every route in RouteTable is terminal. Following them adds no value and turns a method downgrade into a silent false success. Verified with a probe using the same http.Client config: the POST arrived as `GET /capabilities/billing.charge` with the Bearer token and returned 200 with the describe body.
- **How to fix:** In api.NewClient and in the httpClient() fallback, set `CheckRedirect: func(*http.Request, []*http.Request) error { return http.ErrUseLastResponse }`. In do(), map `300 <= status < 400` to a StructuredError (code internal) with the message `base URL redirected to <Location>; re-run auth login with --base-url=<scheme://host[/path]>`. Add one api test (a 301 on POST invoke gives an error, not ok) and one auth test (LoginWithToken against a 301 stores nothing). Tests that inject env.NewClient get the same policy if they build clients through api.NewClient.

### L-102 — Idempotent retries of approval-gated invokes create duplicate approvals
- **Severity:** high · **Effort:** small · **Impact:** reliability, security
- **Locations:** `packages/laravel-capabilities/src/Pipeline/IdempotencyGuard.php:248`, `packages/laravel-capabilities/src/Approval/ApprovalManager.php:228`, `packages/laravel-capabilities/src/Registry/CapabilityRegistry.php:746`
- **Current:** When an invoke with Idempotency-Key K needs approval, the key row is stored as pending_approval. A retry with K and the same body gets lookup() → 'continue', so it re-runs authorize and needsApproval and creates a second pending approval, overwriting the row's approval_id. Nothing ever completes the key: withIdempotency() is never called in production, so completeIdempotency() is a no-op, and executeApproval() does not pass the key either. Retries after execution also open fresh approvals instead of replaying the result.
- **Recommended:** A pending_approval row with the same hash should replay the stored approval_required result (same approval_id). Approved execution should run under the row's idempotency key so the key moves to completed/failed and later retries replay the executed outcome.
- **Why it matters:** D-005 / principle 11: 'Retries must not double-apply … approval accepts are idempotent when a key is supplied'. Spec §D-006 step 5 says run under the original key. CLI --idempotency-key and agents retry on timeouts, so one logical high-stakes action becomes N pending approvals, and accepting each runs the domain N times. That defeats both the approval gate and the key.
- **How to fix:** IdempotencyGuard::lookup: for status pending_approval with a matching hash, return ['action' => 'replay', 'result' => hydrateResult(result_json, false)], unless $options['executing_approval_id'] equals the row's approval_id (then continue). executeApproval(): add 'idempotency_key' => $row['idempotency_key'] to the options. Alternatively wire withIdempotency($app->make(IdempotencyStore::class)) on the manager singleton. Unit test with InMemoryIdempotencyStore + InMemoryApprovalStore: two invokes with the same key produce one approval row; after accept, a third invoke replays the executed result.

### L-101 — Approval requests use an unconfigured second ApprovalManager; notifiers never fire
- **Severity:** high · **Effort:** small · **Impact:** reliability, maintainability
- **Locations:** `packages/laravel-capabilities/src/Registry/CapabilityRegistry.php:550`, `packages/laravel-capabilities/src/Boot/ContainerBindings.php:282`, `packages/laravel-capabilities/src/Pipeline/InvokePipeline.php:733`, `packages/laravel-capabilities/src/Approval/ApprovalManager.php:355`, `packages/laravel-capabilities/src/Approval/ApprovalManager.php:237`, `packages/laravel-capabilities/src/CapabilitiesServiceProvider.php:134`
- **Current:** The provider builds a configured ApprovalManager singleton, but makeRegistry passes only its store, and withApprovalStore() builds a fresh `new ApprovalManager($store)` with default config. Every approval_required from any surface goes through that second instance. It has no notifiers: nothing in core, messaging or AI ever calls addNotifier(), and a host that adds one to the singleton still never sees it fire. It also ignores approval.ttl_hours (request() caps expires_at at the default 24 h), and Capability::approvals() hands out this unconfigured instance.
- **Recommended:** Build one ApprovalManager and use it everywhere: the registry pipeline should take the provider's configured singleton, not a store. The provider should attach every bound ApprovalNotifier (the messaging package already binds TelegramApprovalNotifier to the contract) plus the core HTTP/CLI notifiers the spec promises.
- **Why it matters:** L-002 made approvals reachable, so this path is now live. Spec D-006 / §Contracts: 'Core registers HTTP/CLI notifiers. Messaging package binds ApprovalNotifier channel for Telegram.' Today no approver is ever notified, so the Telegram approval-button flow is dead end to end. A host that sets approval.ttl_hours to 4 still gets 24 h pending rows, and with 72 a capability's approvalTtlHours of 48 is cut to 24.
- **How to fix:** Add CapabilityRegistry::withApprovalManager(ApprovalManager $m) that re-attaches the registry executor, audit and dispatcher, and have makeRegistry accept the manager, called from the provider with $app->make(ApprovalManager::class). In the ApprovalManager singleton closure, if $app->bound(ApprovalNotifier::class), call addNotifier($app->make(ApprovalNotifier::class)). Unit tests: a provider fake app with approval.ttl_hours=4 → the pipeline-requested row expires in 4 h; a bound recording notifier receives notifyPending on approval_required.

### L-106 — Declared approvalPolicy is unvalidated; unknown values fall open to requester self-approve
- **Severity:** medium · **Effort:** trivial · **Impact:** security
- **Locations:** `packages/laravel-capabilities/src/Approval/ApprovalPolicy.php:112`, `packages/laravel-capabilities/src/Approval/ApprovalPolicy.php:65`, `packages/laravel-capabilities/src/Registry/CapabilityDefinitionBuilder.php:210`
- **Current:** Since L-002 the capability's approvalPolicy string is stored on the row and enforced through forRow(). Nothing validates it: the #[Capability] attribute, the fluent builder and discovery all accept any string. A typo such as 'role-finance', 'Role:finance' or 'any-staff' hits the match default arm, which is requester_or_role with the default 'approver' role. So the requester can approve their own request on a capability whose author meant to require a finance role.
- **Recommended:** Reject unknown policy strings when the definition is built: requester | requester_or_role | any_staff | custom | role:<name>. Make the ApprovalPolicy default arm deny.
- **Why it matters:** Approval is the governance gate for high-stakes capabilities, and an authoring typo should fail at boot, not quietly allow self-approval. The fail-open default was harmless while only the global config value reached it. Per-capability policies now reach it too.
- **How to fix:** Add ApprovalPolicy::isKnown(string): bool and throw InvalidArgumentException/BootException in CapabilityDefinition's constructor when approvalPolicy !== null && !isKnown(...). Change `default => false`. Unit tests: builder->approvalPolicy('role-finance') throws; a row with approval_policy 'bogus' denies the requester.

### L-105 — Approved execution is rate-limited as the requester; rate_limited burns the approval
- **Severity:** medium · **Effort:** trivial · **Impact:** reliability
- **Locations:** `packages/laravel-capabilities/src/Pipeline/InvokePipeline.php:169`, `packages/laravel-capabilities/src/Pipeline/InvokePipeline.php:850`, `packages/laravel-capabilities/src/Approval/ApprovalExecutor.php:235`
- **Current:** executeApproval() re-invokes the pipeline as the requester with the original caller, so stageRateLimit spends the requester's per-minute and per-capability buckets. The original request already spent a hit on the same keys. Take a capability declaring rateLimit max=1 (typical for sensitive approval-gated operations) that is accepted within the decay window: execution returns rate_limited. ApprovalExecutor treats every non-ok result as terminal, so the row becomes executed/failed. It cannot be retried; accept replays the failure.
- **Recommended:** Do not rate-limit the execution of an already-approved request. The request was counted when it was made, and the approver is not the requester. Alternatively, treat transient pipeline outcomes (rate_limited, busy) as non-terminal and leave the row approved for resume.
- **Why it matters:** D-013 places the rate limit before approval so requests cannot flood the store. It does not say to limit a decision that was already made. As it stands, a prompt approval of a low-limit capability silently discards the approved action, and the approver sees a retryable error that cannot be retried.
- **How to fix:** In InvokePipeline::stageRateLimit, return null when isset($state->options['executing_approval_id']), the same guard stageNeedsApproval already uses. Unit test: capability with rateLimit ['max' => 1], needsApproval true; invoke → approval_required; accept immediately → executed ok and run() called once.

### L-104 — Audit write failures: silent under best_effort, raw in approvals, leaked in strict
- **Severity:** medium · **Effort:** small · **Impact:** reliability, security
- **Locations:** `packages/laravel-capabilities/src/Pipeline/InvokeAuditStage.php:90`, `packages/laravel-capabilities/src/Pipeline/InvokeAuditStage.php:96`, `packages/laravel-capabilities/src/Pipeline/InvokeAuditStage.php:75`, `packages/laravel-capabilities/src/Approval/ApprovalManager.php:789`, `packages/laravel-capabilities/src/Approval/ApprovalExecutor.php:397`
- **Current:** L-006 now wires DatabaseAuditWriter into production, so its failures are real. Three problems follow. (1) best_effort, the default: a failed insert goes only to InvokeObservation::log(), a capped in-memory window. No PSR log, report() or metric. (2) required=true: the fallback 'durable outbox' is Audit\AuditOutbox, a PHP array on the singleton, never drained and lost when the process exits. (3) strict: the wire message embeds $e->getMessage(), and a QueryException carries SQL plus bound values including payload_json. Approval audit writes (requested/decided/executed) are unguarded, so a failed write throws out of request(), accept() and execute() after state changed or run() committed.
- **Recommended:** Report every audit write failure through the ExceptionHandler/logger and a metric. Make the required-mode fallback durable, or fail boot when required=true has no durable fallback. Return a fixed 'Audit failed.' message in strict mode. Route approval audit writes through the same best_effort/strict policy as invoke audit.
- **Why it matters:** D-010: best_effort means 'log error + metric', required means 'at-least-once via outbox — not silently drop'. Today the default config drops failed audits with no trace, for example when the outbox migration was never run. With required=true they are kept only in RAM, and the array grows without bound in workers during an outage. L-009 sanitized the outer catch but not this path.
- **How to fix:** In InvokeAuditStage::record catch: call report($e) via Container ExceptionHandler, increment an audit_write_failed_total metric, and replace $e->getMessage() on the wire with 'Audit failed.'. Give ApprovalManager/ApprovalExecutor::auditWrite a try/catch that applies the mode (best_effort → report and continue). For required=true, either retry into the same DatabaseAuditWriter later or throw BootException when audit.queue/outbox is not durable. Unit tests: a throwing writer plus a recording ExceptionHandler → reported once; strict wire message contains no exception text; accept() still returns the executed result when the writer throws under best_effort.

### M-106 — Add a per-user unlink for code-bound Telegram identities
- **Severity:** medium · **Effort:** small · **Impact:** security

### L-103 — A throwing bus-event listener turns a committed run() into 'internal' and poisons the key
- **Severity:** medium · **Effort:** small · **Impact:** reliability
- **Locations:** `packages/laravel-capabilities/src/Pipeline/InvokePipeline.php:203`, `packages/laravel-capabilities/src/Pipeline/InvokeResultFinalizer.php:31`, `packages/laravel-capabilities/src/Pipeline/InvokePipeline.php:245`, `packages/laravel-capabilities/src/Pipeline/InvokeResultFinalizer.php:53`
- **Current:** Since L-007, CapabilityInvoked goes synchronously through the host Dispatcher after run(), the completed idempotency write and the success audit. A sync listener that throws, or a queued listener whose queue push fails, propagates to the L-009 outer catch. finishUncaught() then calls finishFailure(), which overwrites the stored 'completed' key with 'failed/internal', dispatches CapabilityFailed and returns 'internal' to the caller. For approvals, ApprovalExecutor records the executed row as result_status=failed although run() committed.
- **Recommended:** Once run() has succeeded, listener failures must not change the invoke outcome or its stored idempotency result. Isolate host listener exceptions: report them, keep the success. Or make finishUncaught skip the idempotency overwrite when STORE_IDEMPOTENCY already completed.
- **Why it matters:** D-010: 'Domain state remains committed'. The failure matrix only allows an error after a successful run for strict audit. Failed rows replay for the whole TTL (IdempotencyGuard.php:200), so the client can never learn about the success. A client that retries with a new key double-applies the mutation. Before L-007 events never left the process, and before L-009 the catch did not rewrite the key, so this combination is new.
- **How to fix:** In InvokeResultFinalizer::dispatch (and the ApprovalManager/ApprovalExecutor dispatch sites), wrap $this->events->dispatch() in try/catch(Throwable) and report through ExceptionHandler, as InvokePipeline::reportThrowable does. Unit test: a Dispatcher fake whose dispatch() throws on CapabilityInvoked; with an idempotency key, the invoke returns ok, the store row stays 'completed', and the exception is reported.

### M-103 — Retry only the failed Telegram reply, not the whole agent turn
- **Severity:** medium · **Effort:** small · **Impact:** reliability, performance
- **Locations:** `packages/laravel-capabilities-messaging/src/Telegram/ProcessTelegramUpdate.php:266`, `packages/laravel-capabilities-messaging/src/Telegram/ProcessTelegramUpdate.php:200`, `packages/laravel-capabilities-messaging/src/Telegram/ProcessTelegramUpdate.php:232`, `packages/laravel-capabilities-messaging/src/Telegram/ProcessTelegramUpdateJob.php:18`, `packages/laravel-capabilities/src/Pipeline/IdempotencyGuard.php:212`
- **Current:** A retryable failure anywhere (Bot API 429/5xx on the reply, a retryable registry result) fails the job, and the retry re-runs the whole update: the chat turn limit is hit again, AgentTurn::respond() calls the LLM again, and tool calls are re-issued. Idempotency keys are 'telegram:<chat>:<update>:<index>' and core scopes them per capability, so they only replay when the new LLM answer repeats the same capability and input at the same index. A different answer runs extra mutations under fresh keys, or conflicts (409) and the update ends silently.
- **Recommended:** The agent turn and its tool invokes run at most once per update. A reply-send failure retries only the send, and a retryable tool result retries the same tool call list, not a new LLM answer.
- **Why it matters:** M-002's fix made the job retry (correct), but the unit of retry is the whole pipeline while only the tool invokes are idempotent. LLM output is not deterministic, so D-005 exactly-once holds only by luck on retry, and each retry pays for another LLM call and appends another turn to any host AgentTurn memory.
- **How to fix:** Option A: on reply failure, dispatch a small SendTelegramReplyJob(chatId, text, topic) with its own tries/backoff and return ok from the update job. Option B: cache the AgentTurn result under 'capabilities-messaging:turn:<chat>:<update_id>' (TTL a few minutes) before invoking tools and reuse it on retry. Unit test: second handle() of the same update after a retryable reply failure does not call AgentTurn::respond again.

### X-101 — Split mirrors tag and workflow_dispatch trees onto package-remote main
- **Severity:** medium · **Effort:** small · **Impact:** reliability, dx
- **Locations:** `.github/workflows/split-packages.yml:19`, `.github/workflows/split-packages.yml:125`, `.github/workflows/split-packages.yml:149`, `docs/versioning.md:137`
- **Current:** Every split run clones package-remote main, replaces its tree with the triggering ref's package tree, and pushes it to main. It does this before it tags, whatever the ref. Tag v0.5.3 (351fea0) is on the hotfix branch fix/l004-bug-errors, not on main: it is v0.5.2 plus one fix and lacks 77 main commits (about 4.6k lines under packages/). The logic means its tag run fast-forwarded all four package remotes' main to that older tree. A workflow_dispatch from any branch does the same.
- **Recommended:** Only a run for refs/heads/main advances package-remote main. A tag run builds its sync commit off to the side (parent: remote main, or no parent) and pushes only the tag. workflow_dispatch is limited to main (or it only re-tags).
- **Why it matters:** versioning.md tells app integrators to VCS-require package `dev-main`, so a regressed main reaches consumers. Nothing reverts it until the next monorepo main push, and cancel-in-progress:false queues runs in order, so a tag run queued after a main run leaves main regressed. The split is the only publication path (AGENTS.md ship model), and hotfix tags already exist in history.
- **How to fix:** In the sync step: `if [[ "$SOURCE_REF" == refs/heads/main ]]; then <existing push-to-main loop>; fi`. For tags: `git -C "$work" commit ...` on a detached HEAD, then `git -C "$work" push origin "HEAD:refs/tags/${tag}" --force` without touching main. Add a job-level guard: `if: github.ref == 'refs/heads/main' || startsWith(github.ref, 'refs/tags/v')` so a dispatch from a feature branch is a no-op.
